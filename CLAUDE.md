# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Reduction Stepper is a small-step operational semantics visualizer for a subset of SML. A `stepper-core` Rust crate parses, typechecks, and single-steps SML-subset programs, compiles to WebAssembly, and is driven by a static `www/` frontend: type in a program, click "Step" repeatedly, and watch it reduce one redex at a time with the next redex highlighted.

The supported language (see `stepper-core/src/frontend/ast.rs`) is real SML syntax, not a look-alike:
- `val` declarations with patterns (`ident`, `_`, literal, tuple `(p1, p2, ...)`) and optional `: type` annotations
- ints and bools; arithmetic (`+ - * div mod ~`, floor-semantics `div`/`mod` matching SML, not Rust's truncating `/`/`%`); comparisons (`= <> < <= > >=`, nonassociative — no `a < b < c`); `andalso`/`orelse` (short-circuiting, right-associative)
- `if e then e else e`; `let decls in e end`; tuples `(e1, e2, ...)`; `case e of p1 => e1 | p2 => e2 | ...`
- non-recursive lambdas `fn p : t => e` (the parameter type is mandatory — there's no unification engine to infer it) and function application `e1 e2`, plus function types `t1 -> t2` (right-associative). Application is left-associative and binds tighter than every infix operator *and* than `~`, exactly as in SML: `f x + y` is `(f x) + y`, and `~ f x` is `(~f) x`.
- No lists, no exceptions, and no exhaustiveness checking on `case` yet. An unmatched `case` or a literal pattern that doesn't match its value panics at runtime (real SML would raise `Match`/`Bind`) — see `view::HighlightColor::Red`, reserved for a future exception indicator.

## Commands

- `make build` — compiles `stepper-core` to WASM via `wasm-pack` and outputs bindings into `www/pkg` (runs `wasm-pack build --target web --out-dir ../www/pkg` from `stepper-core/`).
- `make serve` — builds, then serves `www/` over HTTP on port 8585 (override with `make serve PORT=xxxx`) using Python's built-in server. The frontend must be loaded through this (or another) HTTP server, not opened as a `file://` URL, since ES module imports require it.
- `make test` — runs `cd stepper-core && cargo test`. Prefer this (or `cargo test` directly from `stepper-core/`) over `make build`/`make serve` when iterating on interpreter logic — it's much faster and doesn't need `wasm-pack`.
- `make clean` — removes `stepper-core/target` and `www/pkg` build artifacts.
- Typical workflow after changing Rust code: `cargo test` to check correctness, then `make build` and `make serve` (or just reload the browser if already serving) to check it in the actual UI.

## Architecture

The governing split is **semantics vs. display**. The AST holds only what a program *means*; how it currently *looks* — what's highlighted, which lambdas are folded, how wide the lines are — lives beside it in `view::ViewState`, keyed by `NodeId`. Nothing in `stepping/` reads the view, and nothing in the view is disturbed by a reduction. Two kinds of identity make that work, both minted in `ast.rs`:

- **`NodeId`** on every `Expr` and `Pattern` — *which node is this?* Every live node has an id nothing else shares. A reduction that rewrites a node *in place* reuses its id (`Expr::same_id`) and clones untouched subtrees as they are, so `1 + 2` and the `3` it becomes are the same place on screen and a fold survives steps that don't involve it; a reduction that *duplicates* a subtree gives the copy fresh ids (`subst::fresh_copy`), so two copies of a lambda fold and highlight independently. That second rule is why `step` returns the ids it placed instead of letting callers infer them from the substituted value.
- **`BinderId`** on every variable — *which variable is this?* A binding site and each use of it share one; the `name` alongside is display-only. This is what makes shadowing a non-issue in `subst.rs` and `typecheck.rs`, and what removed the old "rename `fact` to `factA`" machinery from `eval.rs` entirely.

- `stepper-core/src/frontend/` — parsing, resolution and typechecking, purely syntactic/static, no evaluation.
  - `ast.rs` — the AST: `Expr` (a `NodeId` plus an `ExprKind`), `Pattern`, `Binder`, `Type`, `Decl`, `Program` (`= Vec<Decl>`), plus `walk_exprs`/`lambda_ids`. `PartialEq` on `Expr`/`Pattern` ignores ids and `Binder` compares by name, so tests can assert on shapes; nothing else ever compares trees.
  - `grammar.l` / `grammar.y` — the lexer and LALR grammar, built by `lrlex`/`lrpar` (the `grmtools` toolchain) at compile time via `build.rs` into generated parser code — not source, don't hand-edit, and there's nothing to regenerate manually (`cargo build`/`cargo check` does it). Actions mint a *fresh* `Binder` at every identifier, binding or not; `resolve` fixes up the uses.
  - `resolve.rs` — points each variable use at its binding site. Infallible: a use with no binder in scope keeps its own unshared id and so fails `typecheck`'s env lookup, which is where "Unbound identifier" is still reported. This pass is where the scoping rules actually live.
  - `mod.rs` — `parse_program` (parse + resolve), the frontend's only public entry point. Nothing outside the module ever holds an unresolved `Program`.
  - `typecheck.rs` — a small structurally-recursive typechecker, env keyed by `BinderId` (`HashMap<BinderId, Type>`), so shadowing needs no handling at all.
- `stepper-core/src/view.rs` — `ViewState`: the collapsed set, the highlight map, and the layout width, plus `HighlightColor`. Held beside the program, never inside it.
- `stepper-core/src/pretty/` — printing, in three stages: `build.rs` turns a program into a `Doc` (deciding parens from precedence and break *points* from grouping), `doc.rs` lays that out to a given width (Wadler/Lindig: `Group` fits-or-breaks, `Nest` indents, `Align` indents to the current column) producing a flat `Vec<Item>`, and a backend consumes those. `render.rs` is the string backend; `crate::dom` is the DOM one. Parsing a printed program reproduces the same AST **at every width** (tests check 8–80), since a break only replaces a space with a newline. `pretty_print` uses `UNLIMITED_WIDTH`, which keeps every group flat and gives the single-line canonical form. Highlights are resolved at *render* time from `ViewState` — deliberately not baked into the `Doc`, since they can't affect layout. Folds are read while the `Doc` is *built*, since they can.
- `stepper-core/src/dom.rs` — wasm-only. `render_program` returns a real `<pre>` `Element` built with `web-sys`, so the frontend does `output.replaceChildren(render_program())` and contains no rendering logic. Each region gets a `<span>`: `Ann::Class` becomes a token class (`kw`/`op`/`lit`/`var`/`ty`), `Ann::Node` becomes `data-node` plus any highlight class, and lambdas additionally get `data-collapse` for click-to-fold. Clicks are handled by *delegation* from one listener in `index.html`, which is what keeps this module free of `Closure` lifetime management.
- `stepper-core/src/stepping/` — the small-step semantics.
  - `eval.rs` — `step`: performs exactly one reduction on a `Program`, returning the new program, a human-readable message (e.g. `"Evaluated 1 + 2 to 3"`, `"Substituted x = 5"`), and the `NodeId`s it placed (what the display paints green). Nothing needs stripping first — highlights aren't in the tree. `is_value` defines what counts as fully reduced. `REC_ENV` parks `val rec` lambdas keyed by `BinderId`; binding one substitutes *nothing*, since uses already refer to that binder.
  - `highlight.rs` — `highlight_next`: returns the `NodeId` of whatever `step` would act on next, without performing it and without touching the tree. Mirrors `step`'s search order exactly, so it never drifts out of sync; `tests/common`'s `run_to_value` asserts the two agree at every step.
  - `subst.rs` — `substitute` (no *shadowing* checks needed: a different binding is a different `BinderId`, so an inner `fn x` spelled the same simply isn't matched), `refresh_binders`, `try_match`/`destructure` (pattern matching — `try_match` returns `None` on a literal mismatch for `case` to try the next arm; `destructure` is a panicking wrapper used where there's only ever one pattern to satisfy, e.g. a `val` decl).
    - **`fresh_copy` is the one way a subtree may be duplicated**, and both halves of it matter. Each placement `substitute` makes and each lambda `step_var` unrolls goes through it, getting fresh `NodeId`s *and* fresh `BinderId`s for what it binds; free variables (a recursive function's reference to itself included) and all names are left alone. Fresh binders are capture avoidance: without them, continuation-passing style breaks immediately, since every unrolling of `fn res => k (x * res)` reuses one `res` and `k` is then substituted with a previous one, so the outer `res` captures the inner — `recursion.rs`'s CPS test silently returned 3 instead of 6. Fresh nodes are what keep the display honest: `highlight_next` returns a single `NodeId`, so shared ids meant marking a redex in one copy painted the identical spot in every other, and folding a lambda folded all its copies at once. See `highlight.rs`'s `marks_only_the_copy_being_reduced` and `pretty.rs`'s `folding_one_copy_of_a_lambda_leaves_the_others_expanded`.
  - `mod.rs` — re-exports `step` and `highlight_next`; everything else in `stepping/` is private.
- `stepper-core/src/lib.rs` — the `wasm_bindgen` boundary, holding a `thread_local!` `Session` of one program plus its `ViewState`: `enter_formula` (parse + typecheck + store, returning `""` or a complaint — *not* a rendering), `step_formula`, `toggle_collapse`, `set_width`, `foldable_ids`, `current_render` (the marker-string rendering, for tests and debugging; the browser uses `dom::render_program`).
- `stepper-core/tests/` — all tests, as integration tests (`cargo test`) driving the crate's public API only, one file per phase of the pipeline: `grammar.rs` (what parses to what), `pretty.rs` (printing — the parse/print round-trip property, plus line-breaking and folding), `typecheck.rs`, `stepping.rs`, `highlight.rs` (the yellow next-redex preview and green substitution markers), `recursion.rs` (`val rec`, which needs the thread-local recursive-value env reset per test), and `api.rs` (the `lib.rs` wasm-bindgen boundary). A new language feature should get tests in each phase file it touches; test names don't repeat the file name (`grammar.rs`'s `parses_a_case_expression`, not `grammar_parses_a_case_expression`).
  - `tests/common/mod.rs` — shared helpers, included by each file with `mod common;`. `parse`/`expr_of`/`pattern_of`/`type_of` pull one piece out of a parsed program; `show`/`render_next`/`step_once`/`run` drive the stepping ones; `show_at_width`/`show_folded`/`show_highlighted` drive the display ones. `show` and friends render highlights as readable markers — `[y...y]` yellow, `[g...g]` green — so expected strings can be written literally. Because highlights now live outside the program, `common` keeps a per-test-thread `ViewState` that `step_once` updates and `parse` resets, mirroring `lib.rs`'s session; that's what lets a test say `step_once` then `show` without threading a view around. `run`/`run_to_value` also assert, at every step, that `highlight_next` and `step` agree on whether anything is left to do.
  - `common::expr_builders` re-exports an `Expr` *builder* — `Expr::Add(..)`, `Expr::IntConst(..)` — that shadows the AST type in the parser tests. `Expr` is a struct now (id plus `ExprKind`), and the ~140 expected trees in `grammar.rs`/`pretty.rs` are about shapes, not ids; the builders keep them spelled the way the enum used to be. Those files therefore import `Expr` from `common`, not from `stepper_core::ast`.
- `www/` — static frontend, plain JS with ES modules, no build step of its own. `index.html` imports the generated `pkg/stepper_core.js`, calls `init()` to load the WASM binary, then wires buttons to `enter_formula`/`step_formula`/`toggle_collapse`/`set_width` and paints with `output.replaceChildren(render_program())`. It contains **no** program-rendering logic — that all lives in `dom.rs`. The stylesheet is the contract: it styles the classes `dom.rs` emits.
- `www/pkg/` — generated by `wasm-pack build`; not source, do not hand-edit. Regenerate with `make build` after changing anything under `stepper-core/src/`. Gitignored.

## Grammar gotchas

The grammar is LALR (`lrpar`/`grmtools`), built with `RecoveryKind::None` (no interactive error recovery — a parse either fully succeeds or returns an error list) and no `%expect`, so an unresolved shift/reduce or reduce/reduce conflict fails the build. Two constructs are deliberately "open-ended" (no closing keyword) — `if ... then ... else <expr>` and `case ... of <arms>` — so each needs the same trick to stay unambiguous when nested without parens: give the relevant terminal(s) the *lowest* declared precedence (see `%nonassoc 'ELSE'` and `%nonassoc 'OF' '=>'` / `%left '|'` at the top of `grammar.y`), which makes the LALR conflict resolution default to shift, i.e. "attach to the nearest/innermost open construct" — the same resolution real SML gives dangling-else and dangling `case` arms. When adding another open-ended construct, follow this pattern rather than reaching for explicit `%expect`.

The other structural rule is SML's `atexp`/`exp` split, which is how function application gets a precedence *above* the whole `%left`/`%right` table rather than a slot inside it. `AppExpr -> AppExpr AtomicExpr` is plain juxtaposition with no precedence declaration of its own: `AtomicExpr`'s FIRST set is disjoint from `FOLLOW(Expr)`, so the parser shifts another atom whenever one is available and only reduces up to `Expr` when the lookahead can't start one. Consequences worth knowing before touching it:
- A new expression form belongs in `AtomicExpr` only if it's self-delimiting, mirroring the Definition's `atexp` productions — literals, identifiers, `( ... )`, tuples, `let ... end`, and `~ <atom>`. The open-ended forms (`if`, `case`, `fn`) must stay on `Expr`, so they need parens as an application argument, just as in real SML.
- `~` is deliberately *not* a precedence-table prefix operator (it was one, wrongly, before functions existed). It takes an `AtomicExpr`, which is what keeps application tighter than negation and lets `f ~5` parse.
- `pretty/build.rs`'s numeric precedence ladder has to mirror all of this — application at 6, above every infix operator; `~` at 7 — or round-tripping breaks. Anything in `AtomicExpr` may print bare and ignore `min_prec`; anything else may not.
